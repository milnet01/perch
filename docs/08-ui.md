# 08 — UI

The user-facing surface of Perch: tray, config dialog, hotkeys, notifications.

## Principles

- **Tray-first.** The tray icon and its menu are the primary interface. Most users never open the config dialog; they toggle layouts from the menu.
- **Qt Widgets, not QML.** Widgets render correctly everywhere (X11, Wayland, HiDPI, theming) and don't pull in a QML runtime. Perch is not animation-heavy; QML buys nothing here.
- **Native look on Plasma, acceptable on everything else.** PySide6 + the Breeze style gives this for free. GNOME users will see a Qt dialog — this is called out in the README.
- **Progressive disclosure.** The tray shows the 10 actions people use daily. The dialog shows everything else.

## Tray icon

### Icon states

| State | Icon | Tooltip |
|---|---|---|
| Normal | `perch-tray-symbolic` (the bird silhouette) | "Perch — <active profile> / <active layout>" |
| No layout / no profile | same icon, muted | "Perch — idle" |
| Backend degraded | `perch-tray-warning-symbolic` | "Perch — backend disconnected" |
| Awaiting GNOME extension | `perch-tray-warning-symbolic` | "Perch — install the GNOME Shell extension to enable window management" |
| Missing (e.g. UI-only mode, unknown compositor) | `perch-tray-error-symbolic` | "Perch — no compatible compositor detected" |
| No tray host (GNOME Wayland without AppIndicator) | — (see below) | — |

The tray icon follows the user's icon theme; it ships in `hicolor` as a symbolic SVG so it recolours to match the panel. The status variants live at `data/icons/hicolor/symbolic/status/perch-tray{,-warning,-error}-symbolic.svg` and are resolved at runtime via `QIcon.fromTheme(...)` with the bundled SVG as the fallback. In practice the theme lookup misses and the bundled SVG is what renders, so it is searched for under the install prefix (`/app` under Flatpak, `/usr` under an RPM) as well as in a dev checkout — see `src/perch/ui/icons.py` and the `TrayIconState` enum in `src/perch/ui/tray.py`. The warning / error variants overlay a hard-coded amber / red badge on the silhouette; that small splash of colour survives panel recolouring, so a user whose theme inverts the silhouette still sees the state signal. Qt's SVG renderer handles every HiDPI scale factor natively, so no raster variants are shipped.

### Tray on GNOME Wayland — AppIndicator required

Phase 2 research finding: **`QSystemTrayIcon` on GNOME Wayland is not visible out of the box.** GNOME removed tray support in 3.26; the modern path is the `org.kde.StatusNotifierWatcher` / `org.freedesktop.StatusNotifier*` spec, which GNOME users access via the **AppIndicator** extension (widely installed, e.g. via Extension Manager).

PySide6's `QSystemTrayIcon` uses StatusNotifierItem where a host is registered, and silently does nothing where one isn't. `QSystemTrayIcon.isSystemTrayAvailable()` trusts the watcher and can return `True` with no host actually painting, so Perch runs a dedicated probe.

**SNI-host probe (M3 verified, 2026):**

1. On startup, before any tray instantiation, `sni_host_available()` checks:
   - The session bus has an owner for the well-known name `org.kde.StatusNotifierWatcher` (the freedesktop.org `org.freedesktop.StatusNotifierWatcher` rename never shipped — every real host still registers under `org.kde`).
   - The `IsStatusNotifierHostRegistered` property on `/StatusNotifierWatcher` returns `true`. A watcher without a host is a stale/deprecated state and must be treated as "no tray".
2. Implementation uses `sdbus_block` (sync) because the probe runs before the qasync event loop is live and we want the answer synchronously during startup. See `src/perch/ui/sni_probe.py`.
3. If the probe returns False **and** `$XDG_CURRENT_DESKTOP` contains `GNOME` **and** `$XDG_SESSION_TYPE == "wayland"`, Perch surfaces a first-run dialog: *"GNOME doesn't show tray icons by default. Please install the AppIndicator extension to see Perch in your top bar."* (Link to Extension Manager / EGO.) Perch still runs — the config dialog is reachable from `perch --settings` — but the tray is invisible. (This standalone hint is the *recurring* net for later launches; on a genuine first run it is superseded by the setup wizard's tray-visibility row — see §First-run setup wizard.)
4. If the probe returns False on any other desktop, Perch logs a warning and continues; tray icons are almost always present on KDE, Xfce, Cinnamon, MATE, LXQt. No first-run dialog there — Plasma/Xfce users don't need hand-holding, and showing the dialog would be noise.

Perch does **not** ship an AppIndicator compatibility wrapper (e.g. `libayatana-appindicator` via GObject Introspection). `QSystemTrayIcon` + SNI is sufficient everywhere there is a tray host; the GNOME case is a user-provisioning issue, not a code issue.

### Menu structure

Single left-click: opens the menu.
Middle-click: toggles "Pause Perch" (a panic switch — Perch stops moving windows on its own; see below).
Right-click: same as left-click (KDE-native right-click is preferred; left-click tolerated).

The menu is **regenerated and reassigned** whenever Perch's core state changes (active profile, active layout, known windows, pause toggle). `QMenu.aboutToShow` is not used — QTBUG-55911 leaves that signal unemitted on Linux for menus attached to a `QSystemTrayIcon`, so Perch rebuilds eagerly on state-change signals from `perch.core` and calls `tray.setContextMenu(new_menu)`. The previous menu is reparented to the new one and destroyed by Qt.

**"Donate" submenu** → one entry per funding destination, each opening that
page in the user's browser. The destinations mirror `.github/FUNDING.yml`,
which is the source of truth for the list. They are stated in
`src/perch/ui/links.py` rather than read at runtime, because `.github/` is
not shipped in the wheel, the RPM or the Flatpak; a test asserts the two
agree, so a link added to `FUNDING.yml` and not to the menu fails the suite
rather than shipping a menu that is quietly out of date.

**"Report an issue"** → opens the project's GitHub issue tracker.

Both go through `QDesktopServices.openUrl`. Under Flatpak that resolves to
the `org.freedesktop.portal.OpenURI` portal, which is reachable with the
manifest's existing permissions — verified against the running sandbox — so
neither entry needs a network or browser grant.

**"Windows" submenu** → clicking a window opens a small popover with:

- Current geometry (editable: `x`, `y`, `w`, `h`).
- "Forget this window" (removes the remembered geometry).
- "Add rule from this window…" (prefills the rule editor).
- "Exclude this window from Perch."

**"Pause Perch" toggle** (the menu item, or middle-click on the tray icon) — a
panic switch for when Perch's automatic placement is unwelcome. While paused:

- Perch moves **no** window on its own. Every placement decision the reducer
  would make — rule matches, layout application, per-monitor profile
  re-placement, and last-seen geometry restore — is dropped. Perch keeps its
  hands off every window.
- Active layout / profile selection still tracks reality and persists; Perch
  simply doesn't move windows to match until you unpause.
- **Manual snap still works; bulk re-apply does not.** "Snap focused window ▸"
  is a direct command on one window you picked, so it still applies. "Reapply
  rules now" re-evaluates windows through the same gated path, so while paused
  it moves nothing — pause suppresses every placement except a manual,
  single-window snap.
- Unpausing does **not** retroactively rearrange anything — windows that opened
  while paused stay where they are until their next trigger (you re-activate a
  layout, or the window's title / type / state changes). Perch deliberately
  doesn't yank everything back into place the instant you unpause.

## First-run setup wizard

A three-page `QWizard` (`src/perch/ui/onboarding.py`) that reassures new users
Perch needs no configuration, verifies the mechanical prerequisites, and points
the curious at the deeper features. It runs once automatically, and is
**re-launchable at any time** from the config dialog.

### Pages

1. **Welcome** — states the one thing that matters: *"You don't need to
   configure anything. Just move your windows where you like them — Perch
   remembers."* No controls beyond **Next**. This keeps Perch's opt-in
   complexity (rules, layouts, profiles) out of the way on first contact.

2. **Health checks** — three rows. Rows 1 and 3 are genuine checks: each renders
   ✓ (ok) or ⚠ (needs attention) from a pure `check_*()` function, so the status
   logic is unit-testable without a live desktop (same discipline as the tray
   tests). Row 2 (**Start at login**) is not a check but a *preference* checkbox —
   it renders ✓ when on and a neutral grey dot (●) when off, **never ⚠** (see its
   row). So the "pure `check_*()`" testability applies to rows 1 and 3; row 2's
   state is the checkbox widget.

   | Check | Source | Badge |
   |---|---|---|
   | **Tray icon visible** | `sni_probe.sni_host_available()` | ✓ when a host is present. Not present → ⚠: on GNOME Wayland (`sni_probe.is_gnome_wayland()`) shows the AppIndicator install guidance + link (the same copy as the standalone hint — factor that string into a shared helper so the two can't drift). On any other desktop: *"couldn't confirm — Perch still runs; reach it with `perch --settings`."* |
   | **Start Perch at login** | `config.general.start_at_login` — the persisted intent that governs autostart via `autostart.sync_from_config()` at startup | This row is a **preference, not a fault**: it's a checkbox initialised from that stored value (✓ on a fresh install; the field defaults on). The badge tracks the **live checkbox**, so unchecking it flips the row to a neutral off state — turning autostart off is a valid choice, never an ⚠ alarm. Toggling records the desired state, applied via `autostart.sync()` on dismissal. The badge deliberately does **not** consult `autostart.is_enabled()`, which returns `False` on the Flatpak/portal path (it can't cheaply query portal autostart) and would show a false off-state. |
   | **Compositor detected** | the backend selected at startup | Backends expose no display name, so the wizard owns a small `type(backend) → label` map in `onboarding.py` with **one label per real backend** (KWin/Plasma, Mutter/GNOME, Sway, Hyprland, X11). ✓ with that name; ⚠ *"limited mode"* when Perch fell back to `MockBackend` (no compatible compositor). |

3. **Done** — *"That's it. Perch is watching."* plus one unchecked box,
   **"Show me what else Perch can do"**. When ticked, finishing the wizard opens
   the config dialog — the signpost to rules / layouts / profiles. (The guided
   "create your first rule / layout" walkthroughs on the v1.1 roadmap will later
   hook in here.)

### When it shows — the one-time flag

Gated on a new `[general] onboarding_completed` boolean (schema default
`false`; see `docs/02-state-format.md`). One default serves both audiences: a
freshly-seeded config gets `false`, and an upgrading user's existing config
lacks the key so it also parses as `false` — both see the wizard exactly once.

- **Startup control flow (`src/perch/app.py`).** The probes and tray state stay
  unconditional: `have_host`, `gnome`, and `awaiting_extension` are still
  computed exactly as today (they feed `_initial_tray_state`, which drives the
  tray's "awaiting GNOME extension" state on **every** path — do not move those
  computations into a branch). What the first-run gate controls is only *which
  dialog fires*. The gate — `not config.general.onboarding_completed` — is
  **unconditional**: it fires the wizard for *everyone* on first run (X11, KDE,
  GNOME, all desktops), independent of the tray/GNOME condition that gates the
  hint. Concretely, after the probes run:
  - **First run** → the backend is selected first (the Compositor row needs
    it, so `_select_backend()` runs ahead of tray bring-up), then the wizard
    runs modally, and `_maybe_show_appindicator_hint` is **skipped** this
    launch (the tray health-check row already covers the no-tray case — no
    double notification). The `awaiting_extension` tray state is still set
    from the probes above.
  - **Not first run** → today's behaviour unchanged: on GNOME-Wayland-no-host,
    `_maybe_show_appindicator_hint` fires (the recurring safety net for a session
    that still has no tray host).
- **Persisting the flag.** On **any** wizard exit — Finish, Cancel, or
  window-close (Qt routes ✕ and Cancel through the same `reject()`, so hooking
  `QWizard.finished` covers all three) — Perch writes `onboarding_completed =
  true` so it never reappears unprompted. The write goes through `apply_general`
  in `src/perch/config/edit.py`, which takes each `[general]` field as an
  explicit keyword arg (not a block), so the wizard passes the whole block.
- **The autostart toggle must be persisted to config, not just OS-synced.** At
  every startup `app.py` calls `autostart.sync_from_config(config)`, which
  reconciles the OS autostart entry *from* `config.general.start_at_login` — so
  config is the source of truth. If the wizard only called `autostart.sync()`
  (flipping the OS entry) but wrote the *old* `start_at_login` back via
  `apply_general`, the next login would revert the toggle. Therefore:
  - **Finish** → `apply_general(start_at_login=<wizard checkbox>, …,
    onboarding_completed=true)` **and** `autostart.sync(<checkbox>)`. The
    checkbox value is persisted, so `sync_from_config` keeps it next launch. The
    "passes every field from current config" rule carves out `start_at_login` on
    Finish — it comes from the checkbox, not the loaded config.
  - **Cancel / close** → `apply_general(start_at_login=<current config value>,
    …, onboarding_completed=true)`, no `sync()`. The flag is still written, but
    the checkbox change is dropped — cancelling never changes a system setting.
- The key is carried at **five** points, each load-bearing — the note on each
  is the failure it prevents:
  1. `GeneralSettings` in `config/schema.py` holds `onboarding_completed: bool = False`.
  2. `_parse_general`'s read-loop tuple (`config/schema.py`) reads it back. Without it the persisted `true` is never read and the wizard shows every launch.
  3. `_parse_general`'s unknown-key **allowlist set** (`config/schema.py`) accepts it. Without it the *next* config load raises `SchemaError` — a hard startup crash — the moment the wizard writes it.
  4. `apply_general` in `config/edit.py` takes it as a **required** param, not a defaulted one, so every caller is forced to be explicit; a silent default would let a caller clobber the flag. It is deliberately not routed through `_GENERAL_BOOL_KEYS`, which is unused dead code.
  5. `GeneralPage.commit()` in `src/perch/ui/dialog.py` is the **other** `apply_general` caller — it fires on every OK/Apply that touches the General page. The flag isn't user-facing there, so the page passes the current value through unchanged via `current_general()`, reading the typed `self._state.config.general.onboarding_completed` rather than the raw tomlkit document (which yields `None` when the key is absent). Without it every General-settings save would rewrite the flag to `false` and re-trigger the wizard next launch; `test_general_save_preserves_onboarding_completed` locks it.

### Re-launching it

The config dialog's **General** page carries a **"Run setup wizard again…"**
button (on `GeneralPage` in `src/perch/ui/dialog.py`). The page emits
`rerun_wizard_requested` rather than calling the wizard itself — it knows
nothing of the wizard or the backend; `ConfigDialog` owns the hand-off and
calls the same `run_setup_wizard(config, backend, parent)` entry point the
startup path uses, so the wizard is reachable whenever a user wants to
re-check their setup — not only on first run.

Because that page *also* owns the "Start at login" checkbox and its own
autostart-on-commit path, the two mustn't fight over the same setting. The
button therefore **applies the dialog first** (commits any pending General edits
and saves) before opening the wizard, so the wizard reads current config rather
than a stale value and its Finish can't overwrite an unsaved dialog change.
Afterwards it re-seeds the page from what the wizard wrote: the page owns the
same `Start at login` checkbox, and a stale one would be committed back on the
next OK and silently revert the wizard's change.

## Config dialog

Single `QDialog`, resizable, opens from *Configure Perch…*. Left sidebar lists sections; right pane is the active section's editor. Standard OK/Apply/Cancel footer.

### Sections

1. **General**
   - Start at login (checkbox).
   - Restore geometry on open (checkbox).
   - Notify on restore (checkbox, default off).
   - Theme (Auto / Light / Dark).
   - Log verbosity (Info / Debug).
   - "Open config folder" button.
   - "Run setup wizard again…" button — re-opens the first-run setup wizard (see §First-run setup wizard).

2. **Windows**
   - Live table of windows currently known to the backend: Identity, Title, Monitor, Geometry, Desktop, Last-seen (✓ when the identity has a remembered entry in `state.json`).
   - Updated in real time from the backend's `window_opened` / `window_closed` / `window_changed` / `geometry_changed` signals.
   - Per-row actions: **Save as last-seen** (records the window's current geometry into `state.json` under its identity) and **Forget last-seen** (drops the entry). Both actions mark the page dirty; the dialog's Apply / OK triggers `StateStore.mark_dirty()`.
   - Model + page live in `src/perch/ui/windows_model.py` and the `WindowsPage` class in `src/perch/ui/dialog.py`.

3. **Rules**
   - Table of rules in evaluation order.
   - Drag handles in the leftmost column to reorder.
   - "+ Add rule" button opens a rule editor.
   - Per-rule: name, match fields, apply fields, context fields. Each field has inline validation (red outline + tooltip on errors).
   - **Dry-run toggle** — when on, rules are only logged to the trace panel, not applied.
   - **Rules trace panel** (collapsible at the bottom) — last 50 evaluations with timestamp, window identity, chosen rule, decision.

   **Implementation (M3):** `QTableView` backed by a `QAbstractTableModel` that owns a deep-copy of `list[Rule]` as its working store. On OK the dialog returns the new list; on Cancel the caller's original reference is untouched. Drag-to-reorder is `QAbstractItemView.InternalMove` with `setDragDropOverwriteMode(False)` and a `moveRows()` implementation that calls `beginMoveRows` / `endMoveRows` around a pop-and-reinsert on the backing list. A `QStyledItemDelegate` renders the red-outline-on-error indicator by reading a `Qt.UserRole` validation error stashed per cell. `QTableWidget` is deliberately not used — it mixes presentation with state and makes the dataclass round-trip fragile.

4. **Layouts** — `LayoutsPage` in `src/perch/ui/dialog.py`.
   - Split view: left `QListWidget` of layouts; right side holds a description `QLineEdit` and a `QTableView` of entries with Match / Apply summary columns.
   - Layout-level actions: **Add layout** (name prompt), **Rename**, **Delete**.
   - Entry-level actions: **Add entry**, **Edit**, **Delete**, **Move up**, **Move down**. Entry editing opens the modal `EntryEditorDialog` which composes the existing `MatchEditor`, `GeometryEditor`, a Snap-preset combo (built-ins + `[snaps]` names), and monitor / desktop / maximized fields. The dialog rejects the same contradictions the TOML parser does (empty match, `maximized=true` + geometry, fully empty apply).
   - Commit path replays diffs through `perch.config.edit.{add_layout, rename_layout, delete_layout, set_layout_description}` + the per-entry mutators (`add_layout_entry`, `update_layout_entry`, `delete_layout_entry`, `reorder_layout_entries`) on `tomlkit` so the user's comments on the top-level `[layouts.*]` tables survive. Entry-level TOML comments are not preserved — the entries are fully dialog-authored.

5. **Profiles** — `ProfilesPage` in `src/perch/ui/dialog.py`.
   - Left `QListWidget` of profiles; right side has Name / Topology / Default-layout form + a per-layout **overrides table** (one row per `[[profiles.override]]`).
   - Add / Delete buttons for the profile list; the override table has Add / Edit / Delete whose editors reuse `EntryEditorDialog` inside a smaller wrapper dialog that also picks the override's target layout.
   - Topology is free-text (schema: `name:WxH@X,Y;name:WxH@X,Y` sorted) — a future pass can add a "Use current topology" button once live output queries arrive on this dialog.
   - Commit replays diffs through `perch.config.edit.{add_profile, delete_profile, rename_profile, set_profile_field, set_profile_overrides}`. `set_profile_overrides` rewrites the entire `[[profiles.override]]` array wholesale; fully dialog-authored so no comment loss matters.

6. **Hotkeys** — `HotkeysPage` in `src/perch/ui/dialog.py`.
   - One `HotkeyEdit` row per snap preset defined under `[snaps]`.
   - Click to record a combination; clearing removes the binding.
   - Edits persist to `[snaps.<name>].hotkey` via `perch.config.edit.apply_snap_hotkey`. New bindings take effect the next time the backend registers hotkeys (i.e. on backend restart or a hotkey-provider refresh).

7. **Exclusions**
   - `QListWidget` of exclusion patterns with drag-reorder (`InternalMove`) and Delete / Backspace shortcut (via `_DeleteKeyListWidget`) for removal.
   - Add is deferred to direct `config.toml` editing for v1 — matching the Rules page's add-via-TOML pattern.

8. **Import / Export** — `ImportExportPage` in `src/perch/ui/dialog.py`.
   - **Export** button opens `QFileDialog.getSaveFileName`, then copies the current on-disk `config.toml` to the chosen path. Edits pending in other panes must be applied (OK / Apply) first — the export reads disk, not the working copy.
   - **Import** button opens `QFileDialog.getOpenFileName`. The picked file is validated (tomllib parse + `perch.config.schema.validate`); on success, a unified `difflib` diff vs the current file renders in a monospace read-only panel. **Confirm import** atomically replaces `config.toml` via `perch.config.writer.atomic_write`; **Cancel** discards the pending import.

### Validation and error surfacing

- Invalid rules show inline red text on Apply; focus jumps to the first offender.
- Typing a field that references a non-existent output (e.g. `monitor = "DP-5"`) shows a yellow warning icon — not an error, since the output may appear later.
- Config-file parse errors encountered at startup open the dialog on first launch with a banner at the top explaining what failed.

## Notifications

Perch uses `QSystemTrayIcon.showMessage` (which on Linux routes to `org.freedesktop.Notifications`). Events that trigger a notification:

- **On restore** (if `notify_on_restore = true`): "Firefox restored to DP-1 (maximized)."
- **On profile switch**: "Switched to profile 'Docked'."
- **On backend disconnect**: "Perch: backend disconnected. Retrying…"
- **On config reload error**: "Perch: config.toml could not be loaded. Using last known good."

Notifications are *informational*, never actionable — the user doesn't need a notification to take action on a window.

## Hotkeys

Two paths depending on backend capability:

- **Backend-registered** (KWin via KGlobalAccel, X11 via `XGrabKey`): Perch registers the key with the system, system delivers the event, Perch handles it. This is preferred — hotkeys work even if the Perch dialog isn't focused.
- **Self-grabbed fallback**: not implemented in v1. If a backend reports `can_register_hotkeys = False` (Sway, Hyprland), the UI explains that hotkeys must be bound in the compositor's own config, pointing at a CLI invocation of Perch (coming in v1.x).

### Default bindings (shipped but unobtrusive)

None. Perch ships with **zero default hotkeys bound**. The hotkeys section lists them unbound, and the user picks their own. Rationale: any default will collide with some users' existing bindings, and having Perch steal a key on first run is a bad first impression.

A "Load suggested bindings" button offers a common set (`Meta+Left` for left-half, etc.) that the user can accept in one click.

### Key-capture widget (M3)

The per-row picker is `perch.ui.widgets.key_capture.HotkeyEdit`, a thin subclass of `QKeySequenceEdit` with:

- `setMaximumSequenceLength(1)` — Perch accelerators are single chords, not multi-key sequences.
- `setClearButtonEnabled(True)` (Qt 6.4+) — the built-in clear icon unbinds the action.
- A `keyPressEvent` override that filters bare `Key_Super_L` / `Key_Super_R` / `Key_Hyper_L` / `Key_Hyper_R` so modifier-only presses are ignored. On GNOME Wayland and wlroots-derived compositors the Super keysym arrives as `Key_Super_L` rather than `Qt::Key_Meta`, which would otherwise slip past `QKeySequenceEdit`'s built-in modifier filter (QTBUG-62102). KWin applies this transform compositor-side for its own Qt clients (D6828); the widget-level guard makes Perch portable to non-KWin Wayland.
- An `accelChanged(str)` signal carrying the sequence in `QKeySequence.PortableText` form (`"Meta+Left"`, `"Ctrl+Alt+T"`), empty string when cleared. Rejects bare printable keys with no modifier.

**Accelerator string formats.** Perch carries accelerators internally as Qt Portable Text (`Meta+Left`). The `XGrabKey` X11 path and the KGlobalAccel D-Bus path accept this form directly. The `org.freedesktop.portal.GlobalShortcuts` path wants the XDG Shortcuts spec form (uppercase modifier names — `LOGO/CTRL/ALT/SHIFT` — and xkbcommon keysyms), so a `portable_to_xdg()` translator maps at the portal boundary. See [03-backend-interface.md](03-backend-interface.md) §Hotkey accelerators.

**Portal vs direct KGlobalAccel.** `xdg-desktop-portal-gnome` did not implement `GlobalShortcuts` as of the 2026 snapshot; KDE's and Hyprland's portals do. Perch therefore tries the portal first (preferred for sandboxed Flatpak), falls back to KGlobalAccel D-Bus on Plasma-native sessions, and falls back to `XGrabKey` on X11. GNOME Wayland users without portal support cannot register global hotkeys and the UI says so (greyed rows with a tooltip); Perch does not self-grab in v1.

## Logging and privacy

Perch writes its log to `$XDG_STATE_HOME/perch/perch.log` (1 MB × 3 rotated files via `RotatingFileHandler`). That log is a privacy surface — users may upload it to bug trackers or crash collectors, and window titles routinely leak sensitive data (passwords, filenames, URLs, email snippets).

The policy, enforced by `src/perch/logging_privacy.py` and audited in M7.e:

- **INFO-level messages never embed a window title** or its near-equivalents (`name`, `title`, `caption`, `class`, `initialTitle`, `initialClass`, `window_class`). Counts, `app_id`s and geometry coordinates are fine.
- **DEBUG-level messages reference a window by `id` or by the computed `identity` (`app:<app_id>` form), never by title.**
- **Raw backend payloads** pulled straight from KWin's `WindowAdded` callback or Hyprland's `socket2` stream go through `redact_payload()` before `%r` formatting — title-bearing keys are replaced with `<redacted>` while the rest of the structure is preserved for debuggability. Where even the structure is too noisy, the malformed-entry sites use `summarize_keys()` to log just a sorted key-set.
- **`perch --debug` raises the log level but does not relax the redaction rules** — the sanitisers are applied unconditionally.

If you add a new log site that could embed window text, route it through `redact_payload(...)` or `summarize_keys(...)` before the `%r`. The audit in `tests/test_logging_privacy.py` pins the sanitiser's behaviour; extend it rather than bypassing it.

## Accessibility

- Key dialog surfaces carry `setAccessibleName` / `setAccessibleDescription` so orca and KWin's accessibility layer announce them sensibly (sidebar → "Sections", rules table → "Rules table", exclusions list → "Exclusion patterns"). Check-box / combo-box widgets inherit their accessible name from their label automatically.
- Keyboard navigation is complete: the section sidebar receives initial focus, Tab walks sidebar → active page → OK/Apply/Cancel (pinned by an explicit `setTabOrder` chain in `src/perch/ui/dialog.py`), arrow keys move within the sidebar and list/table views, and **Delete / Backspace on the Rules table or the Exclusions list removes the selected row** via in-tree `_DeleteKeyTableView` / `_DeleteKeyListWidget` subclasses (QShortcut + `WidgetWithChildrenShortcut` doesn't fire against `QTableView` — its built-in delete-current-cell handler swallows the key before the shortcut resolver sees it).
- Colour is never the sole carrier of information (error rows also have an icon).
- HiDPI: icons are SVG, geometry values in the dialog are in logical pixels.

## Localization

- All user-visible strings wrapped in `self.tr(...)` on `QObject` subclasses; non-QObject helper code uses `QCoreApplication.translate("<context>", "...")`.
- Translation sources live at `translations/perch_<locale>.ts` (Qt Linguist XML). They are extracted from `.py` with `pyside6-lupdate $(git ls-files 'src/perch/**/*.py') -ts translations/perch_en.ts -source-language en_US` and compiled to `.qm` with `pyside6-lrelease`. Both commands ship with the `PySide6` wheel; no extra build dependency.
- The convention `po/` is deliberately **not** used — it's a gettext signal, and Qt's `.ts` format is not compatible with gettext `.po`. PySide6 ecosystem convention is `translations/`.
- Runtime loading is `src/perch/i18n.py` using `QTranslator.load(locale, "perch", "_", translations_dir)`. Translator instances are **module-level** so Python's GC doesn't reclaim them and silently revert translations — the #1 PySide6 i18n footgun. Lookup order for `translations_dir`: `$PERCH_TRANSLATIONS_DIR` → `/app/share/perch/translations` (Flatpak) → `$sys.prefix/share/perch/translations` (system install) → dev-checkout fallback.
- Localizable content: every UI string, every log message that is *shown* to the user. Log messages that only land in `perch.log` stay English — translating them adds noise for bug reports.

## What the UI does *not* do

- No inline rule editing via dragging windows on a mini-preview of the desktop. Intriguing idea; deferred to v2.
- No visual layout editor ("click where the window goes"). Also deferred.
- No "night mode schedule" or other time-based triggers. Out of scope.
- No status bar presence (just a tray icon). Tray is good enough and more universally supported than custom status-bar integrations.

## Interaction with the rest of the system

- **Menu updates**: the tray menu is regenerated on every open, driven from current state. Not held across opens.
- **Window list updates**: the "Windows" dialog pane subscribes to backend events and updates live.
- **Theme switching**: `src/perch/ui/theming.py::apply_theme(app, config.general.theme)` runs once at startup from `src/perch/app.py::main`. `"auto"` reads `QGuiApplication.styleHints().colorScheme()` (Qt 6.5+): when the platform reports `Qt.ColorScheme.Unknown` Perch leaves the palette untouched (this is the right call on Plasma, where Breeze-Dark handles itself); `Light` / `Dark` get a Fusion-style override with a hand-built Breeze-inspired palette. Explicit `"light"` / `"dark"` values force Fusion + the matching palette unconditionally, so a GNOME user with Adwaita-Dark who prefers a light Perch dialog gets it. Re-applying on runtime system-theme change is deferred (the config-dialog save path already restarts the dialog; global app-wide re-apply without a restart lands in a follow-up).
- **Icon theme**: whatever the user's Qt icon theme is; symbolic icons recolour automatically on Plasma's panel.

## Implementation notes (forward-looking)

- UI widgets live under `perch/ui/`:
  - `tray.py` — `TrayIcon(QSystemTrayIcon)` and menu builder.
  - `dialog.py` — `ConfigDialog(QDialog)` and its section widgets.
  - `widgets/` — re-usable bits (match editor, geometry editor, key capture).
- UI never imports from `perch.backend.*` directly. It reads from `perch.core.state` and fires `perch.core.intents`.
- Tests: `pytest-qt` drives the widget classes; the full dialog is exercised with a `MockBackend` preloaded with representative windows.
